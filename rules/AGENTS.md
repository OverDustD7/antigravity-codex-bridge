# Codex coordination

Use the `codex-conversation-bridge_coordinator` tools to find and read local Codex chats. If the user names a project, pass its name, directory, or ID as `workspaceId` to `codex_list_threads`. Set `activeOnly` when looking for an active chat. Send to the exact chat identified by the user or the project context. Ask when multiple targets fit and the choice changes the work.

- Ask the user to clarify the goal, constraints, and acceptance criteria when needed. Codex owns implementation, tests, and technical verification. Read the project's roadmap and evidence before reviewing a milestone or proposing a change in direction. Use plain language to explain your judgment.
- Use `purpose: coordination` every time you delegate work, direct a project decision, or own milestone acceptance. Use `purpose: message` or omit it for an ordinary question, status check, or fault report. Preserve the original Codex chat and use a stable `requestId` for each dispatch. Default delivery sends directly. Use `delivery: after_turn` when the user wants to wait for the active turn to finish.
- A queued request is awaiting delivery. Use `codex_wait_dispatch` on its original request ID to learn when it is accepted. When waiting for a reply, open `codex_wait` in the background with the originating `conversationId` and the returned `after` cursor. Continue from `nextCursor` after a receipt. If the MCP tools disappear, use the exact fallback command supplied by the session hook. Keep one receipt delivery path per chat pair.
- If Codex exits or restarts, keep the original receipt wait and cursor. Background delivery stays quiet until a real receipt or explicit message arrives. Connection diagnostics and empty interruptions inferred after disconnect are available for manual inspection in the inbox.
- Agree on a reporting cadence that balances Gemini usage with timely course correction. Combine nearby steps and short stages into one update and check in during long stages while a change is still practical. Check the result against the agreed roadmap's goals, acceptance criteria and constraints for the current stage. Reuse relevant sections you have already read if they have stayed the same. Explain the result, key evidence, what changes for the user and the next step in plain language. Contact the original Codex chat only for major drift or an evidence-backed improvement to the next step. Codex continues in the same turn while you review. The milestone needs no acknowledgment.
- Handle real blockers and substantial audience-facing writing through their existing handoff paths. A `turn_fallback` gives the original Codex turn's final output when it ended without an explicit report.
- Tell the user promptly about tool failures. Preserve the original request ID, cursor, and error, and use `codex_inbox` to check for a missed receipt before retrying. Observe the user's authorization when relaying data or taking action in another chat.
